# sagebrush-gpu UI: design (draft r1)

The manager and member web UI. Stack: TypeScript, Preact and @preact/signals, bundled with
esbuild into static assets that the control-plane Worker serves on the API's origin (no CORS,
cookie sessions). It uses only the public API, the same API Sagebrush uses.

## Principles

- **Generic words.** The UI says project, member, team, manager and allocation. A project may set
  display labels (course/student, grant/researcher). They are applied in one place
  (`labels.ts`), never hard-coded in components.
- **Money is exact.** Amounts are integer micro-USD from the API. The UI formats them and never
  does float arithmetic on balances. Prices always show the provider's price and the service
  margin separately: "provider $0.48/h + service $0.14/h = $0.62/h".
- **The server decides.** The UI hides controls the user's role can't use, and it disables Start
  when the quote says `canStart: false`, showing the reason. The server still enforces all of it,
  and the UI shows the server's error if they disagree.
- **No surprises when stopping.** Stop is a save followed by a stop. The UI shows save progress
  and says plainly when a machine was stopped by the service (idle, max session, budget,
  watchdog, provider failure), and why.

## Screens

### Everyone
- **Sign in:** enter an email and receive a link. "Check your email" page.
- **Home:** the user's projects with their role in each. Owners also see their organizations.

### Member (project page, member view)
- **Spend meter:** used, remaining (after the final-save reserve), current rate per hour, and
  time left at that rate ("about 3 h 20 min at $0.62/h"). Colour bands: OK, under 20%, under 5%.
  `asOf` is shown as "updated 1 min ago", since the ledger accrues per minute.
- **Storage:** used of quota for the personal area and, if any, the team area.
- **Start a machine:** a GPU type list (e.g. "1x L4 24 GB") with the price split, from the
  quote. Unavailable types are shown greyed out with a reason (no capacity, over the price cap,
  allocation too low for the minimum slice). Start, then progress: requested, booting,
  restoring the workspace, running the setup script, ready.
- **Machines:** state, GPU, provider, uptime, cost so far. Actions: Open terminal (embedded
  xterm.js over the machine relay), Open Jupyter (a new tab through the relay), Save now (with
  progress), Stop (save progress, then stopped), Restart, Delete.
- **History:** past sessions with cost and stop reason.

### Manager and assistant (project page, manager view)
- **Overview:** budget, spent, remaining, running machines now, spend by day (a small bar chart).
- **Members:** a table with email, team, allocation, spent, remaining, running machines,
  storage and last active. Sortable and filterable. Actions: edit the allocation (one, or bulk
  for the selection: "set to $X" / "add $X"), stop their machines, remove.
- **Invite:** paste a list of emails (one per line or comma-separated), with a preview of the
  valid, duplicate and invalid addresses before sending.
- **Teams:** create, rename, assign members, team allocation, team storage.
- **Policy:** allowed GPU types and providers, max price per hour, idle minutes, maximum session
  length, max concurrent machines, setup script (a code box), display labels, start and end
  dates.
- **Machines:** every running machine in the project, with Stop and **Stop all** (with
  confirmation that names the count).
- **Spend export:** a CSV by member, by team or by day, generated by the server from the ledger.
  It includes provider cost and margin columns.
- Assistants see everything except policy, allocations and the budget (read-only).

### Owner (organization page)
- Credit: balance, top-ups (by invoice, so read-only in the UI for the pilot), and assignments
  to projects. Assign or reclaim credit for a project.
- Managers: invite and remove.

## State and data flow

- One API client (`client.ts`), typed by `@sbgpu/api`'s `Endpoints` and sent with fetch.
  The mock backend (`mock/`) plugs in as a fetch function, so the UI runs the same client
  code against the mock and the control plane. The UI picks the mock with `?mock=1` in
  development.
- Signals per resource (`me`, `project`, `members`, `machines`, `meter`). Polling: every 5 s
  for machines that are changing state, every 30 s otherwise, paused while the tab is hidden.
- The routes are hash-free paths (`/p/:projectId`, `/p/:projectId/members`, `/o/:orgId`). The
  Worker serves `index.html` for unknown UI paths.

## Code layout

- `src/app/`: the web app. `store.ts` holds the state (signals) and the actions; `components.ts`
  holds the screens, written with htm tagged templates, so they run in Node with no JSX build and
  are tested by rendering them to HTML; `router.ts` holds the paths; `main.ts` is the browser
  entry point.
- `src/view.ts`: what each screen shows and allows (state labels, stop reasons, refusal texts,
  which machine buttons, the meter's figures), as pure functions.
- `build.mjs`: esbuild. `node build.mjs` writes `dist/web/` (production: the mock is compiled
  out); `node build.mjs --mock` writes `dist/web-mock/`, where `?mock=1` runs the whole API in
  the page on a fake clock (`&speed=N` fake seconds per real second, default 10).
- `serve.mjs`: a local static server with the app-path fallback, for development:
  `node serve.mjs --mock 5180`, then open `http://127.0.0.1:5180/?mock=1`.

## Pure modules (tested under `node --test`)

- `money.ts`: format micro-USD, parse a manager's dollar input into micro-USD (exact, no floats);
  price splits are rounded alike, so the provider price and the service margin shown always
  add up to the total shown.
- `meter.ts`: remaining, the band, and time left at the current rate.
- `csv.ts`: RFC 4180 escaping, with spreadsheet formula-injection neutralising. It is shared
  with the server's CSV export.
- `emails.ts`: parse and validate an invite list.
- `labels.ts`: display labels, with articles and plurals for role words.

## Terminal and Jupyter (the machine relay's protocol)

- The terminal is xterm.js over a WebSocket to the relay on the UI's own site:
  `/api/relay/v1/page?machine=<id>&chan=terminal`. The first frame is
  `{"t":"hello","token":...}`, with a one-use page token of about 60 s from the control plane.
  The token is never put in the URL.
- Text JSON frames only; PTY bytes are base64. The page acks the bytes it has written into xterm
  (`ack upto`, about every 64 KiB), and pastes are sent in `in` frames of at most 16 KiB decoded.
- Reconnect: the session id is kept in sessionStorage per machine, and the page reattaches with
  it. On `replay`, call `term.reset()`. On `no-session`, open a new session. On close code 4001,
  retry with a fresh token, backing off 1, 2, 4 ... 30 s. On 4403, don't retry.
- Jupyter opens in a new tab on its own per-machine origin, through a one-time link from the
  control plane. It never runs in an iframe on the UI's origin. It comes after the terminal.
- Save now is `POST /v1/machines/{id}/save` on the API. Save progress is read from the machine
  object. The UI never talks to the agent directly.

## The mock backend (`src/mock/`)

An in-memory control plane for development and tests. It covers every browser endpoint of
`@sbgpu/api` with its access rules, and uses `budget.ts` for start checks and hard stops.
`advance(ms)` moves a fake clock one second at a time: machines boot (90 s), accrue one ledger
entry per UTC minute (`entrySplit`), save (120 MiB at 20 MiB/s) and stop (15 s). Test hooks
simulate idle stops and provider failures. `seed.ts` builds a demo world in which every quote
refusal can be reached. The mock is not the control plane: where the contract leaves a choice
open, the file header says which choice the mock makes.

`mutants.json` lists this package's mutants as data (file, from, to, test) for the shared
mutant runner.
